## Leçons Apprises 🎓

### 1. Toujours vérifier les PRs existantes AVANT de commencer
**Erreur:** J'ai implémenté une solution complète sans vérifier si le travail était déjà en cours.

**Impact:** 6 commits de code, 14 tests, et documentation gaspillés. Temps perdu en duplication.

**Prévention:**
```bash
# TOUJOURS faire avant de commencer:
gh pr list --state all --search "in:title keyword"
gh issue view <number> --json body
# Vérifier les commentaires récents
```

### 2. Simpler is Better
**Observation:** PR #201 (cache simple) bat PR #203 (3-layer defense-in-depth).

**Principe:** Ne pas sur-ingéniérer. Une solution simple qui fixe la cause racine est meilleure que plusieurs couches de défense complexes.

### 3. Comprendre le Problème Avant de Coder
**Erreur Phase 1:** eBPF exclusion fixe un symptôme (agent self-observation), pas la cause (redundant re-reads).

**Meilleure approche:** Cache fixe le pattern général et bénéficie tous les processus.

### 4. Questionner Chaque Décision de Design
**Exemple TTL:** J'ai assumé qu'un TTL était nécessaire pour la correctness du cache.

**Réalité:** Cgroup membership est stable. LRU bounds suffisent pour PID reuse.

**Leçon:** Challenger chaque feature: "En a-t-on vraiment besoin?"

### 5. Rate Limiting Est Souvent Overkill
**Tentative:** Ajouter rate limiting comme defense-in-depth (Phase 3).

**Réalité:** Si le cache marche, rate limit ne se déclenche jamais. Si le cache fail, fixer le cache d'abord.

**Leçon:** Ne pas ajouter des safety nets pour des problèmes qu'on n'a pas. Attendre l'évidence.
